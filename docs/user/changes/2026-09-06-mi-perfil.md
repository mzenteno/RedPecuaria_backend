# 2026-09-06 — "Mi perfil": editar datos personales y cambiar contraseña

**Rama:** master
**Commit(s):** _pendiente — se completa al commitear este cambio_

## Qué cambió

Nueva pantalla `app/(main)/profile` (frontend), disparada desde "Mi perfil" en el menú del
`TopBar` (antes no navegaba a ningún lado). Dos tarjetas independientes:

- **Datos personales**: edita `email`/`fullName` reusando el `PATCH /users/:id` ya existente
  (`UpdateUserUseCase`), con el id del propio usuario logueado. `username` se muestra pero no
  se puede editar (identificador de login, sigue sin tener ningún flujo de cambio, ni acá ni en
  el diálogo de edición de `app/(main)/users`).
- **Cambiar contraseña**: nuevo `PATCH /users/me/password` → `ChangeOwnPasswordUseCase` — pide
  la contraseña actual (`PasswordHasher.compare` contra el hash guardado) antes de aceptar la
  nueva (`PasswordHasher.hash`, mínimo 6 caracteres). `userId` sale siempre de
  `@CurrentUser('sub')`, nunca de un parámetro — a diferencia de `ChangeUserTypeUseCase` (un
  admin actuando sobre otro usuario, con su propio chequeo de pertenencia a empresa), acá no
  hace falta: el usuario solo puede cambiar su propia contraseña por diseño de la ruta, no por
  una validación extra.
- `User.changePassword(newPasswordHash)`: nuevo método de la entidad, recibe el hash ya
  calculado (la entidad nunca hashea, esa responsabilidad es de la capa de
  aplicación/infraestructura — mismo criterio que el resto de la entidad).
- `InvalidCurrentPasswordException` (`DomainExceptionCode.UNAUTHORIZED` → HTTP 401): nueva
  excepción de dominio, para cuando la contraseña actual no coincide.
- Sin permiso de menú (`RequirePermission`) en la pantalla — mismo criterio que `/dashboard`:
  no es un módulo de negocio con permiso por rol, es una acción sobre uno mismo que cualquier
  usuario logueado puede hacer.

## Motivo

A pedido del usuario: "Mi perfil" (visible en el `TopBar` desde el diseño inicial) solo cerraba
el menú sin navegar a ningún lado — pidió una pantalla real con los datos del usuario y la
opción de cambiar la contraseña.

## Decisiones de diseño

- **Reusar `PATCH /users/:id` en vez de un endpoint nuevo** para editar `email`/`fullName`: es
  exactamente la misma operación que ya hace un administrador desde `app/(main)/users` — la
  única diferencia es que el propio usuario elige su propio id (`getUserId()` de
  `session-storage`, guardado ahí desde el login) en vez de que se lo pase un admin desde una
  tabla. No había motivo para duplicar el caso de uso.
- **Cambiar contraseña sí necesitó un endpoint nuevo** (`PATCH /users/me/password`, no
  `PATCH /users/:id/password`): la ruta con `me` en vez de `:id` dejó explícito en el diseño
  que esta acción SOLO puede ser sobre uno mismo — no habilita "cambiarle la contraseña a otro
  usuario" ni siquiera para un administrador, evitando la necesidad de una validación de
  permisos separada para eso.
- **La pantalla actualiza sus propios datos con la respuesta del `PATCH`, no con el token**: el
  access token JWT solo se reemite en el próximo login/refresh (limitación ya documentada en
  `frontend/ARCHITECTURE.md` §8) — mostrar el nombre nuevo recién ahí haría parecer que
  "guardar" no funcionó. `useMyProfile` arranca mostrando los datos del token decodificado
  (igual que `TopBar`) pero, tras un `updateProfile` exitoso, reemplaza `fullName`/`email` en su
  estado local con el `User` completo que devuelve el backend.
- **Sin campo "Nueva contraseña" prellenado ni mostrado tras guardar**: a diferencia del
  formulario de "Datos personales" (que sigue mostrando los valores ya guardados, tiene sentido
  seguir viéndolos), el de contraseña se limpia con `reset()` tras un cambio exitoso — no hay
  motivo para dejar la contraseña actual ni la nueva escritas en pantalla una vez guardadas.

## Qué había antes

"Mi perfil" en el `TopBar` solo cerraba el menú desplegable (`onClick={() =>
setMenuOpen(false)}`), sin navegar a ninguna pantalla. No existía ningún endpoint para que un
usuario cambiara su propia contraseña — la única forma de cambiar una contraseña era editando
directamente la base de datos.
